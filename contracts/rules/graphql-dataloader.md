# GraphQL DataLoader Contract & Multi-Tenant Request Isolation Rules

## 1. Overview
The GraphQL DataLoader adapter bridges `@batchLoad` (Node.js), `@batch_load` (Python), and `coalesce.MultiTierLoader` / `coalesce.Loader` (Go) into GraphQL field resolvers to eliminate the N+1 query problem.

## 2. Request-Scoped Registry & Context Isolation
To prevent cross-tenant and cross-user data leakage, each GraphQL execution must receive an isolated loader context:
1. In Node.js: `createGraphQLLoaderContext()` returns a `{ loaders: GraphQLLoaderRegistry }` object to be merged into Apollo / Mercurius / Yoga context. Alternatively, request-scoped context can be stored in an `AsyncLocalStorage`.
2. In Python: `create_graphql_loader_context()` returns a context object or dictionary containing an isolated `GraphQLLoaderRegistry`.
3. In Go: `gqlloader.WithContext(ctx, registry)` or `gqlloader.ForContext(ctx)` attaches and retrieves an isolated loader registry from `context.Context`.

### 2.1 What the registry owns (normative)
The isolation in this section is only real if the batching state itself is per registry, so in every lane:
- **Batch queue, in-flight dedup map and L1 cache belong to the registry**, keyed by (registry, service instance). The same key resolved in two registries MUST produce two batch calls; two concurrent registries MUST NOT be merged into one batch. Nothing cached for one registry may be served to another, and none of it may outlive the registry's dispose. Node and Python implement this by running each load inside an ambient batch scope (`batchLoadScopeStorage` / `batch_load_scope`) that `@batchLoad` / `@batch_load` consult before their own instance or `contextStorage` / `context_var` scope; Go creates a new `coalesce.Loader` per registry.
- **No registry means no sharing.** When a resolver runs with no registry (none on the GraphQL context, none ambient), the load runs in a scope that lives for that single resolver call: it is not batched with other calls and reads no cache left by an earlier call. This fails closed (correct data, N+1 queries) instead of falling back to state shared across requests.
- **Registry lookup order:** the registry on the GraphQL context (`context.loaders` / `info.context["loaders"]` or `info.context.loaders` / `gqlloader.ForContext(ctx)`) wins over an ambient one (`graphQLLoaderStorage` / `graphql_loader_scope()`).
- **Python `create_graphql_loader_context()` has no side effects on any ContextVar.** Overlapping contexts may be cleaned up in any order and from any task. Ambient scoping is opt-in through `async with graphql_loader_scope() as registry:`, whose exit never raises across tasks and never leaves a disposed registry active.
- **Services are resolved by identity, never by class or method name.** `service` may be a pre-built instance (used as-is), a class (instantiated once per registry) or a zero-argument factory (called once per registry). Without a registry a class or factory is built per resolver call. A `method` that does not exist on an instance or on a class is an error when the resolver is defined, not on the first request; a class is always constructed (Node: with `new`), never called as a factory.
- **Go batch context.** The context passed to `BatchFn` keeps the values of the caller that opened the batch (tenant, auth, transaction, trace) but not its cancellation. It carries a deadline only when every caller in the batch has one, and then the latest of them. A caller that cancels gets its own `ctx.Err()` and never fails another caller: a batch abandoned by all its callers before dispatch is discarded, and with `SingleFlight` each waiter waits on its own context. This holds for `coalesce.Loader` and `coalesce.MultiTierLoader` alike; for the latter the same context is passed to `L2Cache.MGet` / `SetMany`. Exception: a `coalesce.Loader` with `SingleFlight` passes `BatchFn` a context with the values but **no deadline**, because waiters that join an in-flight key are not known to the batch and any one caller's deadline could fail another; each waiter still returns on its own deadline, and a `BatchFn` that needs a bound must set its own timeout. A `coalesce.Loader` must therefore not be shared across requests whose `BatchFn` reads identity from the context; go through a per-request `gqlloader.Registry`.

## 3. Resolver Signature & Key Extraction
GraphQL resolvers typically have the signature:
- Node: `(parent: TParent, args: TArgs, context: TContext, info: GraphQLResolveInfo) => Promise<TResult>`
- Python: `def resolve_field(self, info: Info, **kwargs) -> TResult` or `def resolve_field(parent, info, **kwargs) -> TResult`
- Go: `func(ctx context.Context, parent *Parent, args Args) (Result, error)`

The adapter MUST accept:
1. `key`: A function or property extractor that retrieves the batch key from `parent` (e.g. `parent => parent.authorId`).
2. `service` & `method` OR `loader`: The batchLoad function or service method to delegate to.
3. Multiple keys handling: Support scalar lookups (1-to-1: `book.authorId -> Author`) and list lookups (1-to-many: `author.bookIds -> Book[]`).

## 4. Query Coalescing Parity
Across all implementations:
- Given $N$ items resolved in the same query depth level (e.g. 50 authors requesting their books), the downstream batch method MUST be called exactly ONCE with all 50 keys batched together.
- Total database round trips for an author + book list query MUST equal 2 (1 for root authors + 1 for batched books) instead of $N + 1$.

## 5. Coalescing Safety Rules (all lanes)
These apply to `@batchLoad` (Node), `@batch_load` (Python) and `coalesce.Loader` / `coalesce.MultiTierLoader` (Go), with or without GraphQL:
- **A caller that gives up never fails another caller.** Cancelling or timing out one caller (Python task cancellation, Go context) returns that caller's own cancellation and nothing else: other callers waiting on the same key or the same batch still get the value. This holds across batches too: a Go `MultiTierLoader` batch that joined another batch's in-flight query and receives that batch's context cancellation or deadline error, while its own context is live, re-runs the query on its own context. A batch that is still collecting and has lost all its callers is discarded, so a later caller opens a fresh batch instead of joining a cancelled one.
- **Invalidation beats an in-flight load.** `clear(key)` removes the L1/L2 entries and also invalidates any load of that key still in flight: a read issued after `clear` starts a new batch call instead of joining the old one (in Go the single-flight key of the L3 query carries a generation that `Clear` advances, so a later batch can never join a query started before it), and the old load, which may have read the pre-invalidation value, MUST NOT write that value (or a negative entry) back to L1 or L2 when it settles. The caller that started before `clear` still receives the value it read. The L2 write is skipped on a best-effort basis: a write already handed to the L2 adapter when `clear` runs cannot be recalled.
- **Per-scope state dies with its scope.** A batch queue and its L1 cache are owned by their scope (request store / context value, registry scope, or service instance) and MUST become collectable when that scope is; the decorator keeps only weak references to them. Python scope values that cannot be weakly referenced (e.g. a `str` request id) are kept in an LRU bounded to 1024 scopes per decorated function; an evicted scope only loses its cache and batching, never correctness. `clear(key)` without a scope invalidates every live scope and deletes from L2 exactly once.
- **The key is bound by position/name, never guessed from its type.** Python decides whether the first argument is the instance from the decorated function's signature (a leading `self`/`cls` parameter), so any hashable key type (UUID, bytes, Decimal, frozen dataclass) is valid on a plain function; the key may also be passed by its parameter name. A first parameter named `self`/`cls` is the receiver only when a key parameter follows it or the function is defined in a class body, so a plain function whose single parameter happens to be named `self` still gets its key. A function defined in a class body with two or more positional parameters and another receiver name (`this`, `mcs`) is resolved per call: the first argument is the receiver only if its class (or the argument itself, when it is a class) owns the decorated function; otherwise it is the key (a `@staticmethod` with an extra parameter).
- **Plain-object batch results are string-keyed (Node).** When a Node batch function returns a plain object, a non-string caller key is matched by its string form (`1` matches `"1"`), in the L3 phase as in the L2 phase. `Map` and array results are matched by the key itself.
